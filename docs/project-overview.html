autoFT 项目核心架构与使用方式

autoFT 是一个“由 AI 代理驱动”的 LoRA 微调工作台。核心不是做一个复杂平台， 而是把“目标定义 → 配置调整 → 训练评估 → 保留/丢弃”的实验循环固化下来， 让代理围绕 config.py 持续迭代。

项目强调 文件少、上下文小、可持续实验：代理只需要理解极少数关键文件， 就能自主开展实验并把最佳配置保留在当前分支。

一句话理解

人类负责定义目标，代理负责跑实验闭环。

入口：goal.md + config.py
执行：uv run train.py
产出：results.tsv + adapters/

1. 核心思路：把微调工作抽象成自治实验循环

人类输入：定义目标

说明任务、模型方向、数据路径、指标和约束。

这些信息写入 goal.md，成为后续所有实验的判断依据。

代理决策：修改配置

代理读取 goal.md、results.tsv 和 config.py。

再决定下一次尝试什么参数、数据格式、评估函数或 replay 方案。

固定基础设施：训练与验证

train.py 和 prepare.py 是稳定底座。

负责数据装载、时间预算、LoRA 训练、评估、保存 adapter。

设计原则 体现方式 收益
最小代码面 关键逻辑集中在少量文件，实验期基本只改 config.py 代理容易读懂全局，不容易“迷路”
实验可回退 每次改动先提交，效果差则丢弃/重置 分支头部始终接近当前最佳结果
目标与基础设施解耦 goal.md 负责“做什么”，train.py/prepare.py 负责“怎么跑” 换任务时不用重写训练框架

2. 核心架构：文件如何分工

说明层

program.md

代理操作手册，规定实验循环、边界、恢复策略和“不要停”的原则。

目标层

goal.md

定义当前分支的目标、主要指标、数据位置、约束条件和研究方向。

可编辑层

config.py

代理的实验画布，放模型名、LoRA 参数、训练超参、数据格式、自定义评估函数。

固定基础设施

train.py

读取配置后执行训练、评估并输出 grep 友好的摘要结果。

固定基础设施

prepare.py

负责数据自动识别、时间预算、replay 混合、verify、adapter merge 等通用能力。

补充产物：results.tsv 记录实验结果，adapters/ 保存每次实验生成的 LoRA adapter，run.log 记录最近一次训练日志。

3. 运行闭环：一次实验是怎么推进的

1

读现状

读取 goal.md、config.py、results.tsv。

2

定下一次尝试

选超参、LoRA rank、数据格式或评估方法。

3

修改并提交

先改 config.py，再提交，确保实验可回退。

4

训练

执行 uv run train.py，在固定时间预算内完成一次训练。

5

评估与记录

从 run.log 提取 eval_loss 或自定义指标，记录到 results.tsv。

6

保留或丢弃

指标更优 → keep
无提升/更差 → discard/reset

4. 用户视角：怎么使用这个项目

准备环境

  • 克隆仓库
  • 执行 uv sync
  • 准备训练/验证数据

描述目标

  • 告诉代理要做什么任务
  • 确认数据路径与指标
  • 生成 goal.md 与初始 config.py

观察结果

  • 查看 results.tsv
  • 检查 adapters/[commit]
  • 需要部署时执行 merge
场景 你需要做什么 系统会做什么
新建任务 给出任务目标、模型方向、数据位置 创建分支、整理 goal.md、初始化 config.py
持续实验 通常不需要介入 持续修改配置、训练、评估、保留/丢弃
查看最佳结果 打开 results.tsv 或检查分支状态 把当前最佳思路保留在分支头部
导出可部署模型 执行 uv run prepare.py --merge adapters/[best_commit_hash] --output ~/models/my-model 把 LoRA adapter 合并回基础模型

5. 数据与可调能力

模块 支持内容 为什么重要
数据格式 Chat / Alpaca / Completion，支持 .jsonl、.json、.parquet 减少人工转换成本，让更多任务可以直接接入
训练调参 学习率、batch size、epoch、scheduler、LoRA rank/alpha/dropout 等 支撑自治实验搜索空间
自定义函数 config.py 中可定义格式化函数与评估函数 让项目能从“只看 loss”扩展到准确率、F1、ROUGE 等业务指标
Replay Buffer 可混入通用数据，缓解灾难性遗忘 做领域微调时更稳

6. 关键结论

  • 这个项目的本质不是“训练脚本集合”，而是一个 自治实验框架。
  • 架构上最重要的边界是：目标定义 / 可调配置 / 固定基础设施 三层分离。
  • 使用上最重要的动作是：先把目标说清，再让代理围绕 config.py 持续试验。
  • 如果只看一个文件来理解项目，优先读 program.md；如果只看一个可编辑入口，优先看 config.py。
